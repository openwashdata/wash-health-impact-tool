# Factor table governance

Rules for changing the factor tables of the water and sanitation health impact tool. Draft of stage 3 (2026-10-23), written by an agent for Lars Schöbitz and not yet reviewed. The tables are licensed CC BY 4.0.

## 1. What the tables are and where they live

The tool follows one rule: retrieve, do not compute. Every number that enters a calculation is a row in one of six tables under `data/factors/` at the repository root:

| Table | Kind | How rows get there |
| --- | --- | --- |
| `effects.csv` | curated | one row per conversion factor, read from a source by a person and reviewed |
| `adjustments.csv` | curated | one row per use reference, decay, threshold or method constant, read from a source or set as a documented judgement call |
| `pathways.csv` | curated | one row per enterprise output type with its rules |
| `baseline-disease.csv` | rebuilt | generated by `scripts/10_build_baseline_tables.R` from the WHO GHO and DHS pulls (`scripts/09_stage2_baselines.py`) and the typed-in regional values |
| `baseline-exposure.csv` | rebuilt | generated by the same script from the JMP release (openwashdata jmpdata) and the GHO series |
| `factors-schema.csv` | curated | one row per column of the five tables (the data dictionary) |

The `washhealth` package carries a copy of the six files in `inst/extdata/` and as data objects. The copy is built by `pkg/data-raw/factors.R` and stamped; the package never reads `data/factors/` at run time. `data/factors/CHANGELOG.md` records every change to the tables.

## 2. The version stamp

The stamp is the date and the short git hash of the last commit that changed a table file (`data/factors/*.csv`; the changelog beside them does not move the stamp), for example `2026-10-23-55eb4cc`. `washhealth::factors_version()` returns it, and every result, export and rendered report prints it. The stamp names the exact rows a number came from: `git show <hash>:data/factors/effects.csv` reproduces the table.

If the build script runs while `data/factors/` has uncommitted changes, the stamp gets the suffix `-dirty` and a warning. A `-dirty` stamp must never appear in a report that leaves the team.

## 3. Who may change a row

| Role | Who | May |
| --- | --- | --- |
| Table owner | the method lead (at present Lars Schöbitz) | propose and merge changes to the curated tables; run the rebuild script; cut a release |
| Reviewer | a second person with water, sanitation and health evidence experience | approve or reject a change; no curated row changes without a reviewer |
| Approver | Aqua for All's impact lead | approve a release that changes published numbers; decide how past reports are handled (section 7) |

An agent may draft a change but may not merge it. The same person cannot be owner and reviewer of one change.

## 4. How a value is changed

Curated tables (effects, adjustments, pathways):

1. Never edit a value in place and never delete a row.
2. Add a new row with the same identifier (`factor_id`, `adjustment_id`, `pathway_id`), the new value and a new `valid_from` date.
3. On the old row, set `superseded_by` to the new row's `valid_from` date and add a short note saying why. The old row stays in the table; the package retrieves only rows whose `superseded_by` is empty (`current_rows()`), and stops with a message if an identifier has two current rows or only superseded rows.
4. A new identifier (a new factor, a new pathway) needs a row in `pathways.csv` or an `effect_rule` that uses it, otherwise it is dead data.
5. Describe any new column in `factors-schema.csv` in the same change; the build script refuses a table whose columns are not all in the schema.

Rebuilt tables (baseline-disease, baseline-exposure):

1. Do not edit by hand. Change the pull script or the build script, rerun, and commit the regenerated file with the script change.
2. Retrieved rows keep their source URL and year; derived rows state their arithmetic in `derivation`. A missing value stays in the table as a row with an empty value and a `flag` that says what is missing.
3. The old rows live in git history, reachable through the stamp of any past report.

## 5. The review checklist

A reviewer approves a curated row only when every line holds:

- [ ] Source checked: the reviewer opened the source (DOI or URL in the row) and found the value.
- [ ] Locator: the row names the table, figure or section the value was read from.
- [ ] Interval: low and high are the source's confidence interval, or the row says the interval was not captured (the chain then flags `interval_not_available`).
- [ ] Grade: `evidence_grade` is the source review's own rating (GRADE) or "not graded"; `certainty` is the label the tool carries (high, moderate, low, very low).
- [ ] Use rule: `use_rule` says in plain words when the row applies, and the chain's code follows it (point at the function).
- [ ] `valid_from` is set to the date the row becomes current.
- [ ] `superseded_by` is set on the row this one replaces, with a note, or the change adds a new identifier.
- [ ] Notes name every judgement call (why this row and not another; what the value stands in for).
- [ ] Schema: any new column is described in `factors-schema.csv`.
- [ ] Changelog: `data/factors/CHANGELOG.md` has an entry (section 6).
- [ ] Tests: `devtools::test("pkg")` passes after the package copy is rebuilt; a new row that the chain selects has a test that selects it.

For a rebuilt table the checklist is: the script change is reviewed, the request log (`queries/request-log.csv`) records the new pulls, the row counts and the missing-value markers are listed in the changelog entry, and the worked examples (`docs/worked-examples.qmd`) are re-rendered and the differences stated.

## 6. The changelog and the release

Every change to `data/factors/` gets an entry in `data/factors/CHANGELOG.md` with the date, the git hash, the rows changed (identifiers), the reason, the source, who reviewed it, and which outputs change (a list of pathways, or "none" for a documentation edit).

How a change propagates to the package:

1. Commit the table change on `dev` (the stamp takes that commit's hash).
2. Run `Rscript pkg/data-raw/factors.R`; it copies the files, writes the stamp, rebuilds the data objects and regenerates `pkg/R/data.R`.
3. Run `devtools::document("pkg")`, reinstall, run `devtools::test("pkg")` and `devtools::check("pkg")`.
4. Bump the package version in `pkg/DESCRIPTION` (patch for a documentation edit, minor for a value change, major for a schema or method change) and add a line to `pkg/NEWS.md` naming the new stamp.
5. Commit the package copy. A release is a tag on `main` after the pull request from `dev`.

The rebuild script never runs on its own; a stale package copy is visible because `factors_version()` differs from the hash of the last commit touching `data/factors/`.

Sources to check at each update (from the methodology document): the WHO GHO WSH series (a burden update beyond 2019), the yearly JMP release, new DHS surveys for the eleven countries, updates of the pooled estimates (Wolf 2022, the Cochrane sanitation and hygiene reviews, Garn 2022, the Kremer et al. revision with 18 trials). A reasonable rhythm is one planned update per year after the JMP release, plus an unplanned update when a pooled estimate changes.

## 7. Past reports: never silently

A rendered report carries the stamp of the tables it used. When a table changes:

1. The changelog entry lists which pathways and which outcomes change and roughly by how much (re-render `docs/worked-examples.qmd` before and after and state the differences).
2. Reports already issued are not changed. They stay valid as statements about the tables of their stamp.
3. For every issued report whose pathways are affected, the owner runs `washhealth::check_ledger()` on the stored results (the `ledger.csv` of its `export_results()` folder) against the new tables: rows whose `citation_matches` is FALSE or whose id no longer resolves are the ones the change touches. The affected transactions are listed in the changelog entry.
4. The approver decides per affected report whether to issue a dated addendum (same inputs, new stamp, both results side by side) or to leave it. A report is never re-rendered under its old file name; a re-run gets a new date-first file name and names the old stamp and the new one.
5. Ex-ante targets written into a transaction keep the stamp of the run that set them. An ex-post run uses the tables current at the time of the run and states both stamps when they differ; the difference between the two is reported as a method change, not as a change in what the enterprise delivered.

## 8. What the tool refuses to do

- It never fills a missing factor with a guess; a missing value stays missing and the output says so (`not estimable`, a `missing:` flag, or an evidence gap flag).
- It never retrieves a superseded row.
- It never reads the repository's `data/factors/` folder at run time; only its own stamped copy.
- It never changes a value because a user passes a different one at run time; a user who needs a different row passes an edited copy of the tables (`tables = `) and the result then carries that copy's rows in its ledger, which a reader can compare with the published tables.
